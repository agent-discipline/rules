# 작업 기록

작업을 하면서 남기는 문서의 종류와 쓰는 법을 정한다. 요구사항 명세서, 작업 log, NEXT, 측정 로그가 대상이다. 이 문서들은 읽기 좋은 글이 아니라 작업과 검증의 원본이므로, 공통 원칙의 형식 기본값 대신 정해진 틀을 그대로 따른다.

## 언제 적용하나

코드, 설정, 데이터처럼 실행되는 것을 바꾸는 작업을 시작하고 진행하고 끝낼 때 적용한다. 시점마다 쓰는 문서가 정해져 있다.

- 작업을 시작하기 전: 요구사항 명세서
- 작업하는 동안: 작업 log
- 작업을 끝낼 때: log의 완료 요약, 측정 로그 한 줄, NEXT

남기는 문서를 고르는 기준은 하나다. 나중에 목적을 갖고 다시 읽는 문서만 남긴다. 불안해서 쓰는 문서는 만들지 않는다. 불안은 문서가 아니라 검증으로 푼다 [하네스 README].

## 규칙

### 위치

1. 작업 하나의 기록은 바뀐 프로젝트의 `docs/plans/YYYY-MM-DD/작업명/` 폴더에 둔다. 파일은 `requirement-spec.md`와 `log.md` 두 개다 [core §7].
2. 기록은 작업을 실행한 폴더가 아니라 실제로 바뀐 프로젝트에 둔다 [core §7].
3. 문서 작업과 구현 작업을 한 커밋에 섞지 않는다 [core §6].

### 요구사항 명세서

4. 사용자에게 필요한 것을 모두 묻고 답을 받은 뒤에 쓴다. 사용자가 이미 말한 것은 다시 묻지 않는다 [core §1].
5. 맨 위에 사용자의 요청 원문과 질문·답변을 적는다. "이건 건드리지 마" 같은 답변의 어감을 그대로 남긴다. 이후 모든 판단의 입력이 된다 [명세서 틀].
6. 필수 여섯 칸을 모두 채운다. 한 칸이라도 비면 아직 구현을 시작할 수 없다. 뻔한 작업은 칸마다 한 줄로 줄여도 되지만 칸을 비우지는 않는다 [명세서 틀].

   여섯 칸은 목표와 대상, 경계와 불변식, 기준 소스, 금지 영역, 검증 방법, 위험도다.

7. 위험도는 바뀌는 양이 아니라 틀렸을 때의 손실, 낯섦, 모호함, 되돌릴 수 없음으로 판정한다. 사용자가 말한 위험도가 기준보다 낮으면 조용히 따르지 않고 차이를 알린다 [core §3][명세서 틀].
8. 뒤 작업이 기대는 가정을 한두 개 적고, 작업을 시작하자마자 작은 실행으로 확인한다. 일어날지 모르는 실패를 예측해 늘어놓지 않는다 [명세서 틀].
9. 합의한 명세의 목표, 불변식, 범위를 바꾸려면 사용자와 다시 합의한다 [core §1].

### 작업 log

10. 일이 일어난 그때 덧붙인다. 나중에 기억으로 다시 구성하지 않는다 [log 틀].
11. 한 줄은 시각, 사건, 결과나 결정이다. 시도, 실패, 해결, 결정이 순서대로 드러나게 쓴다 [log 틀].
12. 쓰는 사람은 한 명이다. 다른 작업자의 결과는 받은 시각을 밝혀 옮겨 적고, 받지 못했으면 "미회수"라고 적는다 [log 틀].
13. 리뷰에서 나온 지적은 log 안의 표에 적는다. 지적마다 어디서 나왔는지, 근거 위치(파일과 줄), 어떻게 처리했는지, 상태를 남긴다. 표의 칸은 지우지 않는다 [log 틀].
14. 건너뛴 검증은 항목별로 적는다. 해소하면 줄을 긋고 확인한 내용을 한 줄 덧붙인다. 해소하기 전에는 작업이 끝났다고 말하지 않는다 [log 틀].
15. 리뷰나 다른 도구가 지적했다는 사실은 커밋 메시지와 코드 주석에 적지 않고 log에만 적는다 [core §6].

### 완료 요약

16. 작업을 끝낼 때 log 끝에 쓴다. 무엇이 됐는지, 핵심 변경의 전과 후, 배운 것, 남은 일을 적는다 [log 틀].
17. 전과 후의 코드는 쓰기 직전에 실제 파일을 다시 열어 복사한다(공통 원칙의 사실 3번) [core §7].

### 측정 로그

18. 프로젝트의 `docs/measurement-log.md`에 작업마다 한 줄을 적는다. 1분 안에 쓴다 [측정 로그].
19. 열은 정해진 대로 두고 합치거나 빼지 않는다. 값이 없으면 `-`를 적는다 [측정 로그].
20. 재지 못한 값은 "미측정", 나중에 채운 값은 "소급"이라고 적는다. 빈칸으로 두거나 어림한 값을 넣지 않는다 [측정 로그].
21. 시간은 `~30m`, `~2h`처럼 수로 적는다. 수로 적을 수 없을 때만 말로 적는다 [측정 로그].
22. 표는 하나로 유지한다. 작업 이름과 내용에는 `|`와 줄바꿈을 넣지 않는다. 표가 깨진다 [측정 로그].

### NEXT

23. 프로젝트마다 `docs/plans/NEXT.md` 하나만 둔다. 다음 작업 후보를 적는 문서이고, 다음 세션은 이 문서부터 읽는다 [NEXT 틀].
24. 작업을 끝까지 구현하고 검증한 뒤에 쓴다. 미리 예측해서 쓰지 않는다 [NEXT 틀].
25. "생길 수 있는 문제"에는 이번 작업에서 실제로 본 신호와 그 신호가 다음 작업에서 무엇을 깨뜨릴 수 있는지를 적는다. 신호가 없으면 적지 않는다 [NEXT 틀].
26. 끝난 항목은 지우고 "완료"와 작업 폴더 위치 한 줄만 남긴다. 전체는 80줄 이내, 후보는 5개 이내로 둔다 [NEXT 틀].
27. 줄이 넘치면 완료 이력과 버린 후보부터 지운다. 아직 풀리지 않은 보류 항목은 지우지 않는다. 그것만으로 넘치면 사용자에게 알린다 [NEXT 틀].
28. NEXT의 항목은 후보일 뿐 합의한 명세가 아니다. 그 일을 시작할 때는 새 작업 폴더의 명세서부터 쓴다 [NEXT 틀].

## 예외

- 형식 기본값을 따르지 않는다. 표를 값 비교에만 쓴다는 기본값과 달리 log, 측정 로그, 작업 분해는 표로 쓴다. 문단 길이 기준도 적용하지 않는다 [WM-1].
- 급한 수정은 명세서보다 log를 먼저 만든다. 건너뛴 검증과 문서는 log의 "건너뛴 검증"에 빚으로 적고, 갚기 전에는 완료를 선언하지 않는다 [core §1].
- 공통 원칙의 "사실" 절은 그대로 적용한다.
