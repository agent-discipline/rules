# rules

문제 유형별 접근·해결 방식을 규칙으로 정리해, 에이전트가 일관된 방식으로 작업하게 하는 규칙 모음.

## 취지

에이전트에게 같은 종류의 문제를 맡겨도 접근 방식은 매번 달라질 수 있다. 이 저장소는 **문제상황마다 어떤 방식으로 접근하고 해결할지를 규칙으로 정해 둔다.**

- A라는 문제에는 a라는 방식으로 접근한다.
- B라는 문제에는 b라는 방식으로 접근한다.

에이전트들이 이 규칙을 바탕으로 작업하게 해서, 결과물과 작업 과정에 **통일성과 규칙성**을 갖게 하는 것이 목표다.

## harness와의 차이

| | [harness](https://github.com/agent-discipline/harness) | rules |
|---|---|---|
| 정하는 것 | **어떤 절차로 일하는가** | **이 문제는 어떤 방식으로 푸는가** |
| 내용 | 인터뷰 → 명세서 합의 → 구현 → 검증 → 기록 | 문제 유형별 접근 방식과 해결 방식 |
| 적용 단위 | 모든 작업에 공통 | 만난 문제의 유형에 따라 |

두 저장소는 독립적이다. 하네스는 문제의 종류와 무관하게 작업 절차를 잡고, 이 저장소는 그 절차 안에서 만나는 개별 문제의 접근법을 다룬다. 둘을 어떻게 연결할지는 규칙이 쌓인 뒤에 정한다.

## 다루는 문제 영역

| 영역 | 예 |
|---|---|
| 코딩 작업 유형 | 버그 디버깅, 성능 문제, 동시성, 리팩토링, 마이그레이션 |
| 설계·아키텍처 결정 | 모듈 경계, 계층 구조, 패턴 선택, 트레이드오프 판단 |
| 특정 기술 스택 문제 | 특정 기술에서 반복되는 문제와 그 해법 |
| 비코딩 작업 | 리서치, 문서 작성, 분석, 리뷰 |

## 규칙을 정립하는 방식

규칙은 한 번에 써내지 않고, 대화로 하나씩 정립한다.

1. 문제상황 하나를 고른다.
2. Claude가 그 문제에 쓸 수 있는 방법론을 제시한다.
3. 사용자가 그 방법론이 맞는지 검토하고 판단한다.
4. 합의된 접근 방식을 규칙 문서로 남긴다.

방법론의 출발점은 Claude의 제안이고, 채택 여부는 사용자의 검토가 정한다.

## 에이전트에게 전달하는 방식

**라우팅 인덱스 + 조건부 문서** 구조를 쓴다.

- 상시 로드되는 것은 "문제 → 규칙 문서" 매핑 인덱스 하나뿐이다.
- 에이전트는 해당 문제를 만났을 때 그 규칙 문서만 읽는다.

규칙이 늘어도 매 세션의 컨텍스트 비용은 인덱스 크기만큼만 든다.

## 현재 상태

저장소를 막 시작한 단계로, 정립된 규칙은 아직 없다. 디렉토리 구조와 규칙 문서 형식은 첫 규칙을 정립하면서 정한다.
