  - "원본은 그대로 두고 여기에 하나로 정리할 생각이고"
  - 규칙 정립 방식(저장소 README): Claude가 방법론을 제시하고 사용자가 검토·판단한 뒤 문서화.

  - 그림 형식 → "기본 ASCII, 설계 문서만 Mermaid"

## 1. 목표·대상 (필수)

`rules` 저장소에 문서 작성 규칙을 아래 구조로 정리한다. 흩어진 원본의 규칙을 한곳에서 찾고 따를 수 있게 하는 것이 끝이다.

```text
ROUTING.md            무슨 일인가 -> 읽을 규칙 문서 (상시 로드 인덱스)
writing/
  principles.md       공통 원칙과 기본값
  diagrams.md         그림 규칙
  work-records.md     작업 기록 (명세서, log, NEXT, 측정 로그, 완료 요약)
  study-notes.md      학습 노트 (cs, 이슈 카드, 구현 이슈, 실험, 독후감, 세미나, 변천사)
  walkthroughs.md     소스 코드 해설서
  design-docs.md      설계 문서 (유스케이스, ADR, 절차서, 아키텍처 뷰, 인수인계)
  collaboration.md    README, 커밋, 이슈, PR
```

- 1차 묶음: `ROUTING.md` · `principles.md` · `diagrams.md` · `work-records.md` → 사용자 확인.
- 2차 묶음: 나머지 4개 → 사용자 확인.
- README의 "현재 상태" 절을 실제 상태에 맞게 고친다(묶음마다).

## 2. 경계·불변식 (필수)

- 모든 규칙 문서는 같은 네 칸이다: 언제 적용하나 / 규칙 / 예외 / 출처.
- 규칙마다 원본 출처(파일 경로)가 있다. 원본에 없는 규칙을 새로 만들지 않는다. 이번에 사용자가 새로 정한 것(기본값·충돌 판정)은 "2026-11-17 결정"으로 표시한다.
- 원본끼리 다른 부분은 기본값(`principles.md`) 하나와 유형 문서의 예외로만 나타난다. 같은 규칙을 두 문서에 중복해 적지 않는다.
- 기본값: 문단 3~7문장(학습 노트만 한 문장 한 줄) · 표는 값 비교일 때만(작업 기록·대장은 표 유지) · 강조는 문단당 하나 · 특수 기호는 깨지지 않으면 허용(깨지는 매체만 제한) · 그림은 ASCII(설계 문서만 Mermaid).
- 규칙 문서 자체도 이 규칙을 따른다(정향 먼저, 표는 값 비교에만).
- 문서 하나는 120줄 이내를 목표로 한다. 넘으면 유형을 나눌지 사용자에게 묻는다.
- 개인정보·회사명·이력 내용·프로젝트 내부 식별자를 옮기지 않는다(public 저장소).

## 5. 검증 방법 (필수)

- 출처 대조: 규칙 문서의 각 규칙 항목에 대해 출처 파일에서 해당 문장을 다시 찾아 확인한다(메인이 묶음마다 전수, 결과를 log에 기록).
- 형식 점검: 7개 문서 모두 네 칸 제목이 있고, 120줄 이내이며, 문서끼리 같은 규칙이 중복되지 않는다(`grep`으로 핵심 문구 대조).
- `ROUTING.md`의 모든 링크 대상 파일이 존재한다.
- 개인정보 스캔: 이메일·회사명·홈 경로 패턴 0건.
- 묶음마다 사용자 검토(첫 독자 시험 — 읽고 답을 못 찾은 질문이 결함).
